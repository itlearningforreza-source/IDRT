# ADR-004: Oracle: Multi-Source Threshold Signatures

**Status:** Proposed
**Date:** 2026-11-18
**Deciders:** Principal Architect, Senior Blockchain Engineer, Financial Systems Architect
**Technical Story:** ADR-004

## Context

Current oracle uses single EOA key with mock bank data (random numbers). No attestation verification. This is CRITICAL - fake reserve data enables false solvency claims.

## Decision

Implement threshold signature oracle network (3-of-5): 1) Oracle nodes fetch balance from bank APIs (BI-FAST/ISO 20022) 2) Each node signs attestation with its key share 3) Threshold signature aggregated (BLS or Schnorr) 3) Single transaction submits aggregated signature + balance to ProofOfReserve 4) Contract verifies threshold signature against registered oracle set 5) Staking/slashing for oracle misbehavior 6) Circuit breaker: if oracle stale > 1h, auto-pause minting

## Consequences

### Positive
- No single point of failure
- Cryptographic proof of bank data
- Slashing deters misbehavior
- Regulatory compliant

### Negative
- Complexity of threshold sigs
- Oracle node infrastructure
- Bank API integration per node
- Key ceremony for DKG

## Alternatives Considered
- Chainlink Proof of Reserve (managed service)
- API3 Airnode (first-party oracles)
- Custom multi-sig oracle (simpler, less decentralized)
