# ADR-002: Double-Entry Ledger Implementation

**Status:** Accepted
**Date:** 2026-11-18
**Deciders:** Principal Architect, Senior Blockchain Engineer, Financial Systems Architect
**Technical Story:** ADR-002

## Context

The system has no financial ledger. Only TokenEvent table exists for blockchain events. No double-entry accounting, no chart of accounts, no reconciliation, no immutable audit trail. This violates fundamental financial integrity requirements for a fiat-collateralized stablecoin.

## Decision

Implement full double-entry ledger in PostgreSQL with: accounts table (chart of accounts), journal_entries (immutable, hash-chained), journal_lines (debit/credit with balance constraint), reconciliations table. All financial events (mint, burn, bridge, fees, payouts) create balanced journal entries. Database trigger enforces debit=credit on POST.

## Consequences

### Positive
- Financial integrity
- Regulatory compliance
- Auditor confidence
- Reconciliation automation
- Point-in-time reporting

### Negative
- Schema complexity
- Migration required
- Performance consideration for high volume
- Team learning curve
